RHEL 운영 과정에서 접하게 되는 지원 수명 주기, 부팅과 systemd, 로그, 메모리, CPU·디스크·네트워크 성능 지표, Dump와 스토리지 개념을 한 글에 정리했다. 개별 수치 하나로 장애를 판단하기보다 여러 지표와 로그를 같은 시간대에서 함께 확인하는 것이 핵심이다.

## 1. RHEL 지원 수명 주기

### EOL

EOL(End of Life)은 제품이나 릴리스의 지원 수명 주기가 종료되는 시점을 뜻한다. 지원이 끝난 버전은 일반적인 보안 업데이트와 버그 수정을 더 이상 받지 못할 수 있으므로 업그레이드 또는 연장 지원 계획이 필요하다.

### EUS와 ELS

- **EUS(Extended Update Support)**: 특정 RHEL 마이너 릴리스를 일반 업데이트 경로보다 오래 유지할 수 있도록 제공하던 연장 업데이트 정책이다.
- **ELS(Extended Life-cycle Support)**: 일반 유지보수 단계가 끝난 일부 기존 RHEL 버전에 제한적인 지원을 추가로 제공하던 정책이다.

Red Hat의 지원 정책은 변경될 수 있다. 현재는 기존 EUS·ELS 정책이 새로운 **ELCP(Extended Life Cycle Premium)** 체계로 전환되고 있으므로, 실제 운영 계획은 [Red Hat 공식 Life Cycle 문서](https://access.redhat.com/support/policy/updates/errata)에서 대상 버전과 종료일을 확인해야 한다.

## 2. RHEL 부팅 과정

```text
전원 ON
  ↓
BIOS 또는 UEFI
  ↓
POST와 하드웨어 초기화
  ↓
부팅 장치 선택
  ↓
GRUB2 실행
  ↓
Kernel(vmlinuz)과 initramfs 적재
  ↓
Kernel이 CPU·메모리·장치 초기화
  ↓
initramfs가 실제 Root 파일시스템 준비
  ↓
systemd 실행(PID 1)
  ↓
Target과 Unit 활성화
  ↓
로그인 가능한 시스템
```

Legacy BIOS 환경에서는 MBR의 부트 코드가 사용될 수 있고, UEFI 환경에서는 EFI System Partition의 부트 항목을 통해 부트로더를 실행한다. 모든 시스템이 MBR 첫 번째 섹터만 사용하는 것은 아니다.

### GRUB2의 역할

GRUB2는 부팅할 Kernel과 initramfs를 메모리에 적재하고 Kernel 명령행 옵션을 전달한다. 여러 Kernel이 설치되어 있으면 부팅할 버전을 선택할 수도 있다.

부트로더 손상으로 부팅할 수 없다면 설치 ISO의 Rescue 환경에서 다음을 확인한다.

1. 기존 Root, `/boot`, EFI System Partition을 찾는다.
2. 필요한 파일시스템을 마운트하고 기존 시스템에 `chroot`한다.
3. BIOS·UEFI 방식과 손상 범위에 맞춰 GRUB2 패키지와 부트 항목을 복구한다.
4. GRUB 설정을 다시 생성하고 재부팅한다.

명령과 대상 디스크는 부팅 방식에 따라 달라지므로 장치 구성을 확인하지 않고 예시 명령을 그대로 실행하면 안 된다.

## 3. systemd와 Unit

systemd는 Linux의 초기화 시스템이자 서비스 관리자다. Kernel이 초기화된 뒤 PID 1로 실행되며 서비스, 소켓, 마운트, 타이머와 부팅 상태를 Unit으로 관리한다.

| 경로 | 용도 |
|---|---|
| `/usr/lib/systemd/system/` | 패키지가 제공한 기본 Unit |
| `/run/systemd/system/` | 현재 부팅 중 생성된 임시 Unit |
| `/etc/systemd/system/` | 관리자가 만든 Unit과 Override |

관리자 설정은 우선순위가 높은 `/etc/systemd/system/`에 두는 것이 일반적이다. 패키지 파일을 직접 고치기보다 `systemctl edit`으로 Override를 만든다.

```bash
systemctl cat sshd
systemctl edit sshd
systemctl daemon-reload
systemctl restart sshd
```

### 주요 섹션과 항목

- `[Unit]`
  - `After`, `Before`: 시작 순서를 표현하며 그 자체로 의존성을 만들지는 않는다.
  - `Requires`: 강한 의존 관계다. 필요한 Unit 활성화가 실패하면 영향을 받는다.
  - `Wants`: 비교적 약한 의존 관계다.
- `[Service]`
  - `Type`: `simple`, `exec`, `oneshot`, `forking`, `notify` 등 서비스 시작 방식을 지정한다.
  - `ExecStart`, `ExecStop`, `ExecReload`: 시작·종료·재적용 명령이다.
  - `Restart`: 종료 후 재시작 정책이다.
- `[Install]`
  - `WantedBy`, `RequiredBy`: `systemctl enable` 시 어느 Target 등에 연결할지 정의한다.

Target Unit은 여러 Unit을 논리적으로 묶어 시스템 상태와 부팅 단계를 표현한다.

```bash
systemctl get-default
systemctl list-dependencies multi-user.target
systemctl --failed
```

## 4. Journal, rsyslog과 Dump

### systemd-journald

Kernel과 systemd 서비스 등의 로그를 Journal 형식으로 수집한다.

```bash
journalctl -b
journalctl -b -1
journalctl -u sshd
journalctl --since '2026-09-28 09:00:00'
```

`/run/log/journal`은 휘발성 저장, `/var/log/journal`은 영구 저장에 사용될 수 있다. 이전 부팅 로그를 보려면 영구 Journal 설정이 필요하다.

### rsyslog

syslog 메시지를 facility와 severity 등의 조건으로 분류해 파일이나 원격 로그 서버로 저장·전송한다. 대표적인 파일은 `/var/log/messages`, `/var/log/secure`, `/var/log/cron` 등이며 RHEL 버전과 설정에 따라 달라질 수 있다.

### Kernel Dump와 Process Core Dump

- **kdump**: Kernel Panic 당시 메모리를 `vmcore`로 저장한다. 기본 저장 위치는 보통 `/var/crash`이며 `crash`와 해당 Kernel의 디버그 심볼을 이용해 분석한다.
- **Core Dump**: 프로세스 비정상 종료 당시 메모리와 실행 상태를 저장한다. 저장 방식은 `kernel.core_pattern`과 systemd-coredump 설정 등에 따라 달라진다.

```bash
sysctl kernel.core_pattern
coredumpctl list
coredumpctl info PID
gdb 실행파일 core파일
```

Dump에는 메모리 내용과 민감한 데이터가 포함될 수 있으므로 접근 권한과 외부 전달 절차를 관리해야 한다.

## 5. 프로세스 메모리: Heap과 Stack

- **Heap**: `malloc()`, `brk()`, `mmap()` 등을 통해 동적으로 확보하는 영역이다. 잘못 관리하면 메모리 누수와 단편화가 발생할 수 있다.
- **Stack**: 함수 호출 정보, 지역 변수와 매개변수 등이 저장되는 영역이다. 함수가 끝나면 자동으로 회수되지만 크기가 제한되어 과도한 재귀 호출 등은 Stack Overflow로 이어질 수 있다.

프로세스마다 보이는 가상 주소 공간과 실제 물리 메모리 점유량은 다르다.

## 6. free와 /proc/meminfo

```bash
free -h
grep -E 'MemTotal|MemAvailable|Swap|Commit|AnonPages|Dirty|Writeback|Slab|PageTables' /proc/meminfo
```

### free 주요 필드

- `total`: Kernel 예약 영역 일부를 제외하고 OS가 관리하는 물리 메모리 규모다.
- `used`: `free`가 계산한 사용량이다. 버전에 따라 계산 방식이 다를 수 있다.
- `free`: 어떤 용도로도 사용되지 않는 메모리다.
- `shared`: 주로 tmpfs와 공유 메모리에 사용되는 메모리다.
- `buff/cache`: Buffer와 Page Cache, 회수 가능한 일부 Slab 등을 포함한다.
- `available`: 새 애플리케이션이 Swap 없이 사용할 수 있을 것으로 Kernel이 추정한 메모리다. 단순한 `free + buff/cache` 값은 아니다.

Linux는 남는 RAM을 파일 캐시로 활용한다. 따라서 `free`가 작다는 이유만으로 메모리 부족이라고 판단하지 않고 `available`, Swap 입출력, OOM 로그와 프로세스 RSS를 함께 본다.

### /proc/meminfo 주요 항목

- `AnonPages`: 파일에 직접 대응하지 않는 프로세스의 익명 메모리다.
- `Active/Inactive`: 최근 사용 정도를 기준으로 분류된 페이지다.
- `Active(anon)/Inactive(anon)`: 익명 메모리의 활성·비활성 페이지다.
- `Active(file)/Inactive(file)`: 파일 기반 메모리의 활성·비활성 페이지다.
- `Shmem`: 공유 메모리와 tmpfs 등에 사용되는 영역이다.
- `Slab`: inode, dentry 등 Kernel 객체 캐시다.
- `SReclaimable`: Slab 중 필요하면 회수할 수 있는 부분이다.
- `PageTables`: 가상 주소를 물리 주소로 매핑하는 Page Table 사용량이다.
- `Dirty`: 변경됐지만 아직 저장장치에 기록되지 않은 페이지다.
- `Writeback`: 저장장치에 기록 중인 페이지다.
- `SwapCached`: Swap에서 다시 RAM으로 읽었지만 Swap에도 복사본이 남아 있는 페이지다.

## 7. CommitLimit, Committed_AS와 Overcommit

Linux는 프로세스가 메모리를 예약할 때 모든 페이지에 즉시 물리 RAM을 배정하지 않는다. 프로세스가 실제로 해당 페이지에 접근할 때 물리 페이지가 필요한 경우가 많기 때문이다.

- `CommitLimit`: 시스템 전체가 커밋할 수 있는 메모리의 기준값이다.
- `Committed_AS`: 프로세스들에 커밋된 가상 메모리의 합계다. 현재 RAM에 올라온 RSS 합계가 아니며 아직 접근하지 않은 예약도 포함할 수 있다.

```bash
grep -E 'MemTotal|SwapTotal|CommitLimit|Committed_AS|HugePages_Total|Hugepagesize' /proc/meminfo
sysctl vm.overcommit_memory vm.overcommit_ratio vm.overcommit_kbytes
```

`vm.overcommit_kbytes`가 지정되지 않았을 때 Kernel 문서의 기본 계산 개념은 다음과 같다.

```text
CommitLimit = SwapTotal
            + (MemTotal - HugeTLB에 예약된 RAM) × vm.overcommit_ratio / 100
```

기본 `vm.overcommit_ratio=50`인 시스템에서는 흔히 `Swap + RAM의 약 50%`처럼 보인다. 다만 HugeTLB 예약과 `vm.overcommit_kbytes` 설정에 따라 달라질 수 있다.

### vm.overcommit_memory 모드

| 값 | 동작 |
|---:|---|
| `0` | Kernel의 휴리스틱으로 요청 수용 여부를 판단한다. 일반적인 Overcommit을 허용하지만 지나치게 큰 요청은 거부할 수 있다. |
| `1` | 대부분의 메모리 커밋 요청을 허용한다. 실제 메모리가 부족해지면 OOM 위험이 커질 수 있다. |
| `2` | 엄격한 커밋 회계를 사용해 CommitLimit을 넘는 요청을 거부한다. |

**CommitLimit이 엄격한 절대 한도로 적용되는 것은 mode 2일 때다.** mode 0에서도 `/proc/meminfo`에 값은 표시되지만 같은 방식의 강제 상한으로 쓰이지 않는다.

### 왜 RAM 전체를 커밋 한도로 잡지 않는가?

물리 RAM은 사용자 프로세스의 익명 메모리만을 위해 존재하지 않는다. Kernel 코드와 데이터, Page Table, Kernel Stack, Slab, 장치 드라이버와 DMA Buffer, 잠긴 페이지, 네트워크 Buffer, 파일 캐시 등도 RAM을 사용한다.

mode 2는 성공한 메모리 예약을 나중에도 제공할 가능성을 높이기 위해 보수적인 기준을 사용한다. 낮은 CommitLimit은 현재 RAM 사용량을 제한한다는 뜻이 아니라 **프로세스에 약속할 수 있는 커밋 총량을 제한하는 정책**이다.

## 8. Swap과 vm.swappiness

Swap은 RAM의 비활성 페이지를 디스크로 옮길 수 있는 공간이다. 순간적인 메모리 압박을 견디는 데 도움이 되지만 저장장치는 RAM보다 느리므로 지속적인 Swap 입출력은 성능 저하로 이어질 수 있다.

```bash
swapon --show
free -h
vmstat 1
sysctl vm.swappiness
```

`vm.swappiness`는 익명 페이지 회수와 파일 캐시 회수 사이에서 Swap 사용 성향에 영향을 주는 값이다. `0`도 Swap을 절대로 사용하지 않는다는 뜻은 아니다. 워크로드와 RHEL 권장사항을 확인하지 않고 값만 극단적으로 변경하지 않는다.

## 9. top과 Load Average

`top`은 CPU, 메모리, 프로세스 상태를 실시간으로 확인한다.

- `load average`: 1분·5분·15분 동안 실행 가능 상태 또는 인터럽트 불가능한 대기 상태에 있던 작업 수의 평균이다. CPU 코어 수, I/O 대기와 함께 해석한다.
- `us`: 사용자 영역 CPU 시간
- `sy`: Kernel 영역 CPU 시간
- `ni`: Nice 값이 조정된 사용자 프로세스 시간
- `id`: 유휴 시간
- `wa`: I/O 완료를 기다린 시간
- `hi/si`: Hardware·Software Interrupt 처리 시간
- `st`: 가상머신이 Hypervisor에 양보한 CPU 시간
- `VIRT`: 프로세스의 전체 가상 주소 공간
- `RES`: 현재 물리 RAM에 상주하는 영역
- `SHR`: 공유 가능한 상주 메모리

`PR`과 `NI`는 관련 있지만 같은 값은 아니다. 낮은 Nice 값은 일반적으로 더 높은 CPU 우선순위를 요청한다.

## 10. vmstat, pidstat, iostat, sar

### vmstat

```bash
vmstat 1 5
```

- `r`: CPU에서 실행 중이거나 실행을 기다리는 작업 수
- `b`: 인터럽트 불가능한 대기 상태의 작업 수
- `swpd`: 사용 중인 Swap
- `si/so`: 초당 Swap In·Out
- `bi/bo`: Block Device 읽기·쓰기
- `in/cs`: Interrupt와 Context Switch
- `us/sy/id/wa/st`: CPU 시간 비율

인수 없이 한 번만 실행한 값은 부팅 이후 평균 성격이 강하다. 현재 추세를 보려면 `vmstat 1 5`처럼 간격과 횟수를 지정한다.

### pidstat

```bash
pidstat -u -r -d -p PID 1
pidstat -w -p PID 1
```

프로세스별 CPU, 메모리, I/O와 Context Switch를 시간 간격으로 확인한다. `sysstat` 패키지에 포함된다.

### iostat

```bash
iostat -xz 1
```

- `r/s`, `w/s`: 초당 읽기·쓰기 요청 수
- `rkB/s`, `wkB/s`: 초당 읽기·쓰기 데이터량
- `r_await`, `w_await`: 요청의 평균 대기와 처리 시간
- `aqu-sz`: 평균 I/O Queue 길이
- `%util`: 장치가 I/O를 처리한 시간 비율

빠른 NVMe와 병렬 I/O 환경에서는 `%util=100`만으로 장치가 최대 성능에 도달했다고 단정할 수 없다. 지연시간, Queue, 처리량과 워크로드 기준값을 함께 비교한다.

### sar

```bash
sar -u
sar -r
sar -S
sar -d
sar -n DEV
sar -q
```

`sar`는 수집된 과거 성능 데이터를 조회할 수 있어 장애 발생 당시 상태를 확인하는 데 유용하다. 단, `sysstat` 수집이 사전에 활성화돼 있어야 한다.

## 11. IRQ, CPU 전원 관리와 NUMA

### IRQ와 irqbalance

IRQ(Interrupt Request)는 NIC나 Storage Controller 같은 장치가 CPU에 이벤트 처리를 요청하는 신호다. 특정 CPU에 Interrupt가 집중되면 병목이 생길 수 있으며 `irqbalance`가 여러 CPU에 IRQ를 분산한다. 지연시간에 민감한 워크로드는 무조건 자동 분산하기보다 Vendor와 애플리케이션 권장 구성을 확인한다.

### P-State와 C-State

- **P-State**: CPU가 동작 중일 때 주파수와 전압 등 성능·전력 수준을 조정한다.
- **C-State**: CPU가 유휴 상태일 때 일부 회로를 비활성화한다. 깊은 상태일수록 전력은 절약되지만 깨어나는 지연시간이 늘 수 있다.

```bash
cpupower frequency-info
cpupower idle-info
cpupower monitor
```

### NUMA

NUMA는 다중 CPU Socket 시스템에서 각 Socket이 가까운 Local Memory를 가지는 구조다. 다른 Node의 Remote Memory에도 접근할 수 있지만 지연시간과 대역폭이 다를 수 있다.

```bash
lscpu
numactl --hardware
numastat
cat /proc/PID/numa_maps
```

- `numa_hit`: 의도한 Node에서 할당된 횟수
- `numa_miss`: 요청한 Node가 아닌 곳에서 할당된 횟수
- `local_node/other_node`: 실행 CPU와 같은·다른 Node에서 할당된 횟수
- `node distances`: Node 간 상대적인 접근 비용

`numactl`과 `taskset`으로 CPU·메모리 배치를 제어할 수 있지만, 변경 전 실제 NUMA 병목이 있는지 측정해야 한다.

## 12. Namespace와 CGroup

- **Namespace**: 프로세스, Network, Mount, 사용자 등의 관점을 격리해 각 프로세스가 독립 환경처럼 보이게 한다.
- **CGroup**: 프로세스 집합의 CPU, Memory, I/O 같은 자원 사용량을 계층적으로 관리하고 제한한다.

컨테이너는 이 Kernel 기능들을 조합해 격리와 자원 관리를 구현한다. 가상머신처럼 별도의 Guest Kernel을 실행하는 구조와는 다르다.

## 13. 네트워크 상태 확인

### NetworkManager와 firewalld

NetworkManager는 NIC와 Connection Profile을 관리하며 IP, Gateway, DNS, Route, VLAN과 Bonding 설정을 담당한다. firewalld는 Kernel의 Netfilter 기능을 바탕으로 Zone, Service와 Port 단위 접근 정책을 관리한다.

```bash
nmcli device status
nmcli connection show --active
firewall-cmd --get-active-zones
firewall-cmd --list-all
```

### ss와 tcpdump

```bash
ss -lntup
ss -tnp
tcpdump -i ens160 -nn port 443
tcpdump -i ens160 -nn host 192.168.1.100 -c 100
tcpdump -i ens160 -nn -w capture.pcap
```

`ss`는 Socket과 TCP·UDP 연결 상태를 확인하고, `tcpdump`는 인터페이스를 지나는 Packet을 캡처한다. Packet Capture에는 인증 정보와 업무 데이터가 포함될 수 있으므로 범위와 보관을 관리한다.

### TCP 연결과 종료

3-Way Handshake는 `SYN → SYN/ACK → ACK` 순서로 통신 가능 여부와 초기 Sequence Number를 확인해 연결을 만든다. 일반적인 정상 종료는 양방향을 각각 닫기 때문에 `FIN → ACK → FIN → ACK` 형태로 나타난다.

## 14. LVM, NFS와 DM-Multipath

- **LVM**: PV를 VG로 묶고 LV로 나눠 저장 공간을 논리적으로 관리한다.
- **NFS**: 원격 서버의 파일시스템을 로컬 디렉터리처럼 마운트해 공유한다.
- **DM-Multipath**: 하나의 Storage LUN으로 가는 여러 경로를 하나의 논리 장치로 묶는다.

```text
하나의 LUN
  ├─ Path 1 → /dev/sdb
  └─ Path 2 → /dev/sdc
             ↓
        DM-Multipath
             ↓
      /dev/mapper/mpathX
             ↓
       LVM 또는 File System
```

Multipath는 경로 장애 시 다른 경로로 I/O를 이어 가고, 정책에 따라 경로를 분산해 사용할 수 있다. 파일시스템이나 LVM은 개별 경로인 `/dev/sdb`, `/dev/sdc`가 아니라 Multipath Map을 대상으로 구성해야 한다.

```bash
multipath -ll
findmnt
showmount -e NFS서버주소
```

## 15. 장애 확인의 기본 흐름

```text
현상·발생 시각·영향 범위 확인
  ↓
서비스와 프로세스 상태 확인
  ↓
Journal·애플리케이션 로그 확인
  ↓
CPU·메모리·디스크·네트워크 지표 확인
  ↓
최근 변경과 외부 장치 상태 확인
  ↓
가설별로 한 가지씩 검증
  ↓
조치 후 같은 지표와 로그로 재확인
```

성능 명령어의 한 번 출력만으로 원인을 확정하지 않는다. 정상 시 기준값을 확보하고 장애 시간대의 추세, 관련 로그와 애플리케이션 응답을 함께 비교해야 한다.
